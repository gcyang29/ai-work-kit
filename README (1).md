# AI Work Kit 2.0 | AI Native 실무형 해커톤 대응 가이드

> **목적:** 비개발자가 AI를 활용해 낯선 실무 문제를 180분 안에 정의, 구현, 검증하고, 구현 내용을 스스로 설명하기 위한 **범용 작업 지침**입니다. 특정 시험 문제의 정답이나 사전 작성된 결과물이 아닙니다.

## 0. 가장 먼저 읽을 것 (1분)

1. **시험 규정, 실제 과제 README, 제공 데이터, 담당자의 확인된 답변이 이 가이드보다 우선**합니다. 이 저장소의 README를 실제 과제의 README로 덮어쓰지 마세요.
2. 파일 반입, 공개 Git clone, 외부 접속, Skill 사용이 **허용된 경우에만** 적용합니다. 시험 내용, CSV, 개인정보, 결과물, 로그를 이 공개 저장소에 업로드하거나 Git push 하지 않습니다.
3. AI 사용이 허용된 **3시간 구현 단계**에서만 AI를 활용합니다. **AI 사용이 금지된 30분 서술형 단계**에서는 AI를 호출하지 않습니다. 서술형 문제를 사전에 열람하는 것도 규정상 허용된 경우에만 합니다.
4. 목표는 특정 프레임워크 사용이나 복잡한 알고리즘 채택이 아니라 **요구사항 충족 + 실제 실행 증거 + 설명 가능한 설계 결정**입니다.
5. AI가 '완료'라고 말해도 실제 실행/테스트 결과가 없으면 **미검증**입니다.

## 1. 이번 전략의 핵심: PM처럼 정의하고, AI를 지휘하고, QA처럼 검증

| 관점 | 응시자(사람) | AI에 위임 | 확인할 증거 |
|---|---|---|---|
| Intent: 의도/업무 판단 | 문제, 우선순위, 대안, 현업 승인 판단 | 요구사항 표, 질문, 대안 분석 | 승인/미확정 기록, 완료 조건 |
| Technique: 결과 품질 | 핵심 기능 직접 시연/확인 | 설계, 구현, 테스트, 보안 점검 | 실행 로그, 테스트 결과, 실제 데이터 출력 |
| Cognition: 이해 | 기술 선택 이유 및 한계 설명 | 쉬운 설명, 코드 위치 안내 | 실제 파일/함수와 일치하는 설명 |

> 위 세 축은 학습 프레임이며 **해당 시험의 공식 배점이나 합격 기준을 의미하지 않습니다.**

## 2. 180분 운영표 (현장 상황에 따라 조정)

| 시간 | 목표 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 0~20분 | 규정/과제/데이터 분석, 담당자 질문 및 역제안 | 필수/선택/금지/미확정 조건과 우선순위 확보 |
| 20~40분 | 구현 범위, 아키텍처, 검증 기준 결정 | 입력 → 계산 → 저장 → API → 화면 흐름 및 최소 시나리오 합의 |
| 40~120분 | 작은 단위로 데이터/핵심 로직/API/화면 구현 | 실제 데이터로 최소 1개 핵심 업무 흐름 작동 |
| 120~160분 | 엣지케이스, 보안, 데이터 정합성, UI 사용성 검증 | 요구사항별 PASS/FAIL/NOT TESTED 근거 |
| 160~180분 | 실행환경/제출 검증, 설계 설명 복습 | 제출 경로/파일/실행 조건/미완료 내역 확인 |

**안전장치:** 90분이 지나도 실제 데이터가 연결된 기능이 없으면 애니메이션/디자인/부가기능을 중단하고 가장 중요한 업무 흐름 1개에 집중합니다. 150분 이후에는 새로운 대형 기능을 시작하지 않습니다. 제출 전 검증 시간은 절대 없애지 않습니다.

## 3. 시험 시작 3분: 시작 프롬프트

실제 과제 저장소(원본 작업 폴더)에서 Codex에 입력하세요. 이 가이드가 규정보다 우선하도록 지시하지 마세요.

```text
현재 폴더의 실제 과제 README, 제출 규정, 데이터 파일, 기존 코드를 먼저 읽어줘.
이 저장소의 범용 SKILL.md는 참고하되 실제 과제 요구사항과 충돌하면 실제 과제가 우선이야.
아직 구현하지 마.
1) 필수/선택/금지/비기능/제출 조건 분류
2) 각 조건의 원문 근거 위치와 검증 방법
3) CSV·DB·인증·운영규칙의 위험 및 누락 조건
4) 별도 현업 채팅에 내가 보낼 우선순위 질문 5개와 역제안 (채팅 자동 접근 불가)
5) 반드시 직접 확인해야 할 결정 3개
를 짧게 요약하고, 상세 내용은 규정상 허용된 작업 폴더의 docs/requirements.md에 기록해.
확인된 사실 / 제안 / 미확정을 섞지 마.
```

## 4. 실제 시험 화면 구조: Codex CLI와 현업 채팅은 분리됨

```text
┌ Codex CLI (개발) ┐       ┌ Cofa Probe 현업 채팅 (대화) ┐
│ README/CSV/코드 읽기 │       │ 질문·역제안·현업 답변           │
│ 설계/구현/테스트     │       │ 대화 이력은 플랫폼에서 관리     │
└─────────┬──────────┘       └────────────┬──────────────┘
          │                  자동 연결되지 않음 │
          └────────── 응시자가 필요한 결정만 전달 ┘
```

**확인된 시험 조건: AI 현업 담당자와의 실제 채팅 로그도 평가에 사용됩니다.** 따라서 채팅은 정보를 얻는 수단인 동시에 지원자의 문제 정의, 경청, 역제안, 협의, 의사결정 과정을 보여주는 독립적인 평가 흔적입니다. 다만 **Codex가 오른쪽 채팅을 자동으로 읽거나 내보내지는 못합니다.** 평가 시스템의 로그 보관과 Codex의 접근 권한은 별개이며 두 창은 **응시자가 허용된 범위에서 직접 연결**합니다.

### 대화 로그가 채점되므로, 채팅창 자체에 남길 5가지 행동

1. **문제 재확인:** 현업이 말한 불편을 자기 말로 요약하고 중요한 목표를 확인한다.
2. **정량 기준 질문:** 빈도, 우선순위, 허용 범위, 예외 상황을 하나씩 묻는다. 답변이 없는 기준을 만들어내지 않는다.
3. **선택 가능한 대안 제시:** A/B안의 사용자 편의, 운영 제약, 구현 범위를 짧게 비교해 제안한다.
4. **승인 여부 명확히 확인:** '있으면 좋다'와 '그 방향으로 진행'을 구별하고, 결정 사항을 채팅에서 다시 확인한다.
5. **결정과 한계 요약:** 채팅 안에 확정/미확정/향후 운영자 판단 항목을 간단히 남긴다. 평가자가 채팅 로그만 보아도 의사결정 과정을 알 수 있도록 한다.

**주의:** 평가용 대화를 과장하거나 의미 없는 질문을 양산하지 않는다. 실무 문제를 실제로 해결하는 대화를 한다. 채팅 로그를 Codex 문서에 전부 복제하는 것은 불필요하다.

**현업 채팅에 직접 남길 의사결정 확인 템플릿:**

```text
말씀해 주신 목표는 [문제/우선순위]로 이해했습니다.
A안 [대안/장단점], B안 [대안/장단점] 중 [추천안]을 제안합니다.
[제약조건]은 필수 기준으로 확정해도 될까요?
승인되면 [구현 범위]에 반영하고, [미정 항목]은 운영자 설정 또는 미확정으로 남기겠습니다.
```

### 현업 대화를 Codex에 반영하는 3가지 상황

| 가능 상태 | 응시자가 할 일 | Codex가 할 일 |
|---|---|---|
| A. 복사/붙여넣기 허용 | 업무에 필요한 **짧은 원문 또는 요약**만 CLI에 전달 | 받은 텍스트만 바탕으로 결정을 분류하고, 필요 시 작업 폴더에 기록 |
| B. 복사/내보내기가 불가하지만 직접 입력 가능 | 대화 직후 **핵심 결론 한두 줄**을 기억해 CLI에 직접 입력 | 사용자가 입력한 내용만 반영, 정확한 원문/확답으로 과장 금지 |
| C. 두 화면 간 내용 전달 제한 또는 금지 | 규정을 우선하고, 허용된 범위에서 **본인이 직접 판단하여** 작업 방향만 지시 | 채팅 접근을 시도하지 않으며 확인 불가능한 정책을 확정하지 않음 |

**최소 전달 형식 (20초 메모):**

```text
[현업 반영] 주제: ____
확인한 사실: ____
담당자 답변: ____ (직접 인용 / 내 요약 구분)
결정 상태: 확정 / 조건부 / 참고 / 미확정
구현 지시: ____
```

대화를 통째로 옮기려고 시간을 쓰지 마세요. 기능/제약/우선순위를 바꾸는 핵심 결정만 전달하면 충분합니다. 현업 채팅 로그는 평가 자료이지만, Codex 쪽 문서 기록이 자동 생성되는 것은 아닙니다. 데이터 반입/이동/저장은 시험 규정이 허용할 때만 수행하고, 실제 대화가 복사 불가하면 기록 가능한 범위만 적습니다.

**Codex에 처음 전달할 환경 선언:**

```text
실제 시험은 Codex CLI(개발)와 별도의 AI 현업 담당자 채팅창으로 진행해.
너는 현업 채팅창과 그 대화 이력에 접근할 수 없어. 내가 CLI에 직접 전달한 답변만 사실로 취급해.
현업 질문이 필요하면 내가 채팅에 보낼 짧은 질문/역제안을 먼저 작성해.
내가 결과를 전달하기 전에는 답변이나 승인을 임의로 가정하지 마.
대화 내용이 복사 불가능할 수 있으니 필수 결정만 1~2줄로 전달받아 진행해.
```

## 5. 현업 담당자가 '모른다'고 하면: 역제안 스크립트

**나쁜 방식:** '다른 규칙 없나요?'를 반복하거나, 승인 없이 임의의 기준을 확정.

**좋은 방식:** 문제 확인 → 선택 가능한 A/B안 제시 → 영향 설명 → 결정 요청 → 기록.

```text
현재 확인된 사실은 [확인된 사실]입니다.
결정이 필요한 부분은 [결정 대상]입니다.
A안: [방법], 장점 [ ], 단점 [ ]
B안: [방법], 장점 [ ], 단점 [ ]
제 추천은 [안]이며 이유는 [업무 효과/제약]입니다.
이 방향으로 진행해도 될까요? 결정이 어려우면 운영자 설정값으로 둘 수 있지만,
기본값은 임시 가정으로 표시하고 확정 전에는 검증 필요로 남기겠습니다.
```

담당자가 '모른다'고 하면 **미확정으로 기록**하세요. '있으면 좋다'는 답변은 필수 승인이 아닙니다. 현업 답변과 과제 README가 충돌하면 실제 과제 규정을 우선하고 충돌을 기록합니다.

**Codex에 직접 전달한 결정만 기록하세요. 전체 채팅 이력 자동 동기화를 가정하지 않습니다.**

**결정 로그 형식:** `ID / 질문 / 대안 / 확인된 답변(원문 요지) / 확정·임시·미확정 / 구현 영향 / 확인 필요`

## 6. 개발 시작 전에 반드시 확인할 아키텍처 경계

```text
사용자 화면(UI)
    ↓ 요청/응답
API Controller: 인증, 요청/입력 검증, HTTP 상태코드
    ↓
Business Service: 업무 흐름 조정, 트랜잭션, 실행 상태
    ├─ Algorithm/Optimizer: 계산, 제약조건/비용 비교 (가능하면 DB/HTTP와 분리)
    ├─ Validator: 계산 결과의 필수 조건 위반 여부 확인
    └─ Repository: DB 읽기/쓰기
                      ↓
                    Database
```

이것은 **개념적 권장 분리**이지 모든 과제에서 특정 프레임워크, DB, 큐를 반드시 도입하라는 뜻이 아닙니다. CSV→파싱/검증→계산→결과 검증→저장→API→화면의 각 경계를 질문할 수 있어야 합니다.

- **동기/비동기:** 계산 시간이 짧다면 단순 동기도 가능. 오래 걸리는 작업이 응답성을 해치면 비동기 작업/상태 조회 검토. 비동기가 계산 자체를 자동으로 빠르게 만들지는 않음.
- **트랜잭션:** 함께 성공해야 하는 여러 데이터 변경은 원자성 보장. 중복 요청 및 동시 수정도 테스트.
- **알고리즘:** 먼저 Hard Constraint(위반 불가)와 Soft Constraint(최적화 목표)를 분리. 군집화/그래프/휴리스틱/솔버 등은 데이터와 제약에 따라 선택하며 특정 해법 강제 금지.
- **기술 선택:** 기존 코드와 시험 환경을 우선. React, NestJS, FastAPI 등의 선택 이유와 대안만 설명할 수 있으면 됨.

## 7. 구현 요청 프롬프트 (기능 단위 반복)

```text
확정된 요구사항 중 우선순위가 가장 높은 다음 기능 하나를 구현해.
먼저 입력, 처리, 출력, 완료 조건, 실패 시 동작을 제시해.
실제 제공 데이터와 연결하고 더미 결과를 실제처럼 표시하지 마.
Controller/업무 로직/DB 책임을 구분하고, 가능하면 계산 모듈은 순수 함수로 만들어 테스트 가능하게 해.
구현 뒤 실제 테스트를 실행하고 PASS/FAIL/NOT TESTED를 근거와 함께 남겨.
한 단계가 끝나면 변경 파일, 실제 명령 결과, 설계 이유, 남은 위험을 8줄 이내로 요약해.
이후 docs/decision-log.md 및 docs/essay-notes.md를 업데이트해.
```

## 7. 독립 리뷰 / 보안 / 엣지케이스

코드를 작성한 에이전트의 '성공' 주장만 믿지 마세요. 필요한 경우 별도의 읽기 전용 검토를 요청하세요. 같은 파일을 여러 에이전트가 동시에 수정하지 않도록 합니다.

```text
지금은 새 기능을 만들지 말고 실제 코드와 실행 결과를 독립적으로 검토해.
실제 과제 요구사항별 PASS/FAIL/NOT TESTED, 근거 파일/테스트를 정리해.
특히 원본 데이터 누락/중복/타입 오류/경계값, 0건 조회, 동시 요청, 잘못된 권한,
비밀번호 저장 방식, 비밀정보 노출, SQL injection 방어, API 오류 상태,
알고리즘의 필수 제약 위반, 저장 실패/롤백, 화면-DB 결과 불일치를 확인해.
취약점과 치명적 오류를 먼저 보고하고 우선순위순으로 수정안을 제안해.
테스트 미실행 항목을 통과라고 쓰지 마. 기능 삭제나 인증 우회로 테스트를 통과시키지 마.
```

**보안 기본선:** 평문/단순 MD5/SHA-256 비밀번호 저장 금지. 검증된 비밀번호 해싱(예: Argon2id, 상황에 따라 bcrypt)과 고유 솔트 사용. 인증과 권한 구분, 서버 측 입력 검증, 파라미터화된 쿼리, 비밀정보의 환경변수 관리, 민감정보 로그 최소화. README의 취약한 예제 코드를 그대로 복제하지 말고 규정에 맞게 수정/위험 기록.

**검증 우선순위:** (1) 필수 업무 규칙 (2) 인증/보안/데이터 무결성 (3) 서버 실행/제출 규격 (4) UI 가독성 (5) 장식적 기능. 단 실제 과제에 명시된 우선순위를 먼저 따릅니다.

## 10. 30분 서술형을 위한 개발 중 학습

**시험 규정상 AI가 허용된 구현 단계에만** 본인 프로젝트에 대한 이해를 돕는 기록을 만드세요. 서술형 문제가 비공개라면 사전 열람을 시도하지 마세요. AI 금지 단계에서는 이 Skill도 사용하지 않습니다. 별도 메모 반입/열람 가능 여부도 규정에 따릅니다.

각 핵심 기능 완료 후 AI에게 아래 6개를 실제 코드 기준으로 설명받아 **스스로 말할 수 있는지** 확인하세요.

1. **문제/현업 결정:** 어떤 문제와 제약을 확인했고, 무엇을 제안·승인받았는가?
2. **아키텍처/CRUD:** UI→API→Service→DB의 역할과 실제 파일은?
3. **데이터:** CSV/입력→검증→계산→JSON/DB→화면 경로는?
4. **알고리즘:** 목표 함수, Hard/Soft 조건, 대안과 트레이드오프는?
5. **안정성:** 동기/비동기, 트랜잭션, 인증 및 보안의 구현 이유는?
6. **검증/실패:** 어떤 오류를 어떤 증거로 찾고 수정/재검증했는가?

답변 기본 구조: **문제/목적 → 실제 구현(파일/함수) → 선택 이유/대안 → 실제 테스트 결과/한계**. 구현하지 않은 기능을 구현했다고 말하지 마세요.

```text
방금 완료한 기능에 대해 비전공자인 내가 AI 없이 설명할 수 있도록
'목적 / 실제 처리 흐름 / 코드 파일 위치 / 왜 이렇게 선택했는지 / 확인된 테스트 / 한계'를
각 1~2문장으로 설명해. 이해를 확인할 짧은 질문 2개도 내줘.
실제 코드를 근거로 하고 가정은 분명하게 구분해.
```
