# AI Work Kit 3.0 — AI Native 실무형 해커톤 운영 매뉴얼

> **용도:** 3시간 실무형 과제에서 응시자가 PM/프로덕트 오너로서 **문제 정의 → 현업 협의 → AI 개발 지휘 → 검증 → 인수인계**를 관리하기 위한 범용 참고 가이드.  
> **대상 환경:** Codex CLI + 분리된 AI 현업 담당자 채팅창 + 별도 후속 서술형(6문항, 각 5분).  
> **중요:** 이 README는 *실제 시험 과제의 README가 아니다*. 실제 시험 규정과 해당 과제 README가 항상 우선한다. 특정 스택, 도메인, 알고리즘을 강제하지 않는다.

---

## 0. 60초 요약 — 시험 화면을 켰을 때 볼 것

1. **실제 과제 README부터 읽는다.** 제출 형식, 필수 요구사항, 데이터, 실행조건, 금지사항을 확인한다. 이 문서로 과제 README를 덮어쓰지 않는다.
2. **요구사항에 즉시 구현을 시작하지 않는다.** 불명확한 운영 규칙, 보안 취약점, 누락된 완료 기준을 먼저 찾는다.
3. **현업 채팅에서는 질문만 반복하지 않는다.** 문제 확인 → 수치/우선순위 질문 → A/B 역제안 → 승인 또는 미확정 기록 순으로 진행한다.
4. **Codex에는 실제로 확인된 사실만 전달한다.** 현업 채팅과 CLI는 독립적이다. 채팅 로그가 자동으로 전달된다고 가정하지 않는다.
5. **완료 = 구현 + 실행 검증.** AI의 '완료' 보고만 믿지 않고 입력 → 계산 → 저장 → API → 화면까지 핵심 시나리오를 확인한다.
6. **제품의 판단과 이유를 사람이 이해한다.** 왜 이렇게 만들었는지, 무엇을 검증했는지, 어떤 한계가 있는지 직접 설명할 수 있어야 한다.
7. **마감 15분 전에는 신규 기능 추가를 멈춘다.** 실행, 필수 파일, 제출 절차, 미검증 항목을 확인한다.

**절대 잊지 말 것:** 좋은 AI Native 역량은 AI에게 많은 것을 시키는 능력이 아니라, **목표·제약·품질을 통제하고 결과를 이해하는 능력**이다.

## 1. 시험 규정 및 공개 GitHub 참고 원칙

> 아래는 사용자가 제공한 **2026-10-31 시험 필수확인사항 브리프 및 공개 도구 안내 이미지**를 기준으로 정리했다. 재시험 공지가 바뀌면 최신 안내를 우선한다.

- 공개된 AI Skill/MCP/Plugin 활용 및 GitHub 공개 도구 다운로드: **브리프상 허용**.
- 외부 공개 소스코드 참고, 일부 알고리즘 차용: **허용**. 단, 완성 결과물을 통째로 대체하지 않는다.
- 과제 풀이용 AI: **시험에서 제공한 Codex만** 사용한다. 허가되지 않은 별도 AI 모델/서비스 연결 금지.
- 실제 시험 문제, 입력자료, 현업 채팅내용, 코드, 결과물, 로그 등을 외부로 전송하거나 개인 저장소에 Push하지 않는다.
- 감독, 보안, 화면 공유, 파일 업로드 제한을 우회하지 않는다. **Computer Use(자동 조작) 금지**.
- 후속 서술형은 **AI 사용 금지, 복사/붙여넣기 금지, 본인이 직접 답변**. 서술형 단계에서 이 문서 또는 AI 지원 사용 가능 여부는 당일 규정에 따른다.
- 공개 GitHub에서 사전 작성한 **범용 운영 매뉴얼을 참고**하는 것과 실제 시험 문제의 답안을 미리 준비하거나 외부로 내보내는 것은 다르다.
- 브리프가 새로운 재시험에 그대로 적용되는지는 확인 전까지 **조건부**로 본다. 운영상 애매하면 시험 환경의 공식 안내/Cofa Helper로 확인한다.

### 공개 저장소에서 읽기 (규정과 실행 환경이 허용할 때만)

```bash
git clone https://github.com/gcyang29/ai-work-kit.git
```

- **시험 과제 폴더 밖에** 별도로 받아서 참고한다. 실제 과제 `README.md`를 교체하거나 덮어쓰지 않는다.
- Clone이 차단되면 네트워크·보안 우회를 시도하지 않는다. 허용된 방식으로 README를 읽거나 없이 진행한다.
- Clone만으로 Skill이 자동 활성화되는 것은 아니다. 이번 운영에서는 추가 Skill 설치를 전제로 하지 않는다.
- 위 문서는 **준비용 범용 지침**이다. 실제 시험 코드를 미리 만들어 대체하지 않는다.

## 2. 실제 운영 구조: 세 주체, 두 개의 분리된 창

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **나 (PM / Product Owner)** | 목표·우선순위 결정, 현업 대화, 중요한 설계 선택 승인, 수용 기준 및 제출 판단 | 모든 세부 코드를 직접 작성하려고 하지 않음 |
| **AI 현업 담당자 채팅** | 업무 문제, 실제 불편, 운영 정책, 대안과 허용 범위 협의 | 개발 구현, 코드 검증을 수행한다고 가정하지 않음 |
| **Codex CLI** | 파일/데이터 분석, 설계안 제시, 구현, 실행, 테스트, 원인 분석, 짧은 기술 설명 | 현업 채팅의 내용을 자동으로 알고 있다고 가정하지 않음 |

### 현업 대화 로그의 처리 원칙

- **실제 현업 채팅 로그도 평가 대상**이라는 시험 안내를 기준으로, 채팅 안에 문제 정의, 대안, 승인 여부가 자연스럽게 드러나도록 한다.
- 현업 채팅은 Codex CLI와 자동 연동되지 않는다. 직접 전달이 허용되면 **구현 방향에 영향을 주는 결론만** 짧게 전달한다.
- 채팅 복사가 불가능하면 허용된 범위에서 **본인이 요약해 입력**한다. 전달 자체가 금지되면 우회하지 않는다.
- **사실 / 담당자 승인 / 담당자 의견 / 미확정 / 응시자 가정**을 혼동하지 않는다.
- 현업이 '모른다'고 하면 승인으로 간주하지 않는다. 필요하면 선택지를 제안하고, 최종 미확정 사항은 한계로 기록한다.
- 로그가 평가된다고 해도 질문 개수를 늘리기 위해 불필요한 대화를 반복하지 않는다. **의사결정을 앞으로 진행시키는 대화**를 목표로 한다.

**Codex에 전달할 최소 형태**

```text
[현업 협의 결과 — 내가 직접 확인한 요약]
주제: ...
담당자 발언/확인된 사실: ...
담당자에게 제안한 방향: ...
승인 여부: 승인 / 거절 / 보류 / 미확정
구현에 반영할 조건: ...
반영하지 않을 가정: ...
이 내용만 사실로 취급하고 PLAN.md에 반영해. 현업 대화 원문을 네가 읽었다고 가정하지 마.
```

## 3. 시간 운영: 180분, 6단계 게이트

| 시간 | 단계 | 내가 할 일 | Codex에 맡길 일 | 통과 게이트 |
|---|---|---|---|---|
| **0–20분** | ① DISCOVER | 실제 README, 제출물, 현업 문제 파악 | 요구사항/데이터/보안 위험/질문 후보 추출 | 해결할 문제와 필수조건을 말할 수 있음 |
| **20–40분** | ② DEFINE + DESIGN | 현업 역제안, 우선순위, 설계 방향 승인 | 최소 PRD, 데이터 흐름, 완료 기준, 최소 아키텍처 | 핵심 입력→처리→저장→화면 경계 이해 |
| **40–115분** | ③ BUILD | 15~25분 단위 진행 점검, 주요 결정 | 실제 데이터 기반 필수 기능부터 구현·실행 | 핵심 시나리오가 끝까지 동작 |
| **115–150분** | ④ INTEGRATE | 사용자 흐름을 직접 확인 | API/DB/UI 연동, 오류 수정, 예외 테스트 | UI 조작이 실제 처리 결과와 연결 |
| **150–165분** | ⑤ VERIFY | 위험순위로 테스트 확인 | 요구사항·보안·동시성·실행/환경 검증 | PASS/FAIL/미검증과 근거 확보 |
| **165–180분** | ⑥ HANDOFF | 신규 기능 중단, 제출 확인, 기술 판단 복습 | 파일/명령/경로 점검, 요약 문서 정리 | 제출 누락 없음, 직접 설명 가능 |

> 특정 문제가 어려워 40분을 넘겨도 설계만 하지 않는다. **필수 기능의 첫 실제 입력→출력 흐름을 빠르게 관통**해야 한다. UI는 '예쁜 더미 화면'보다 '실제 데이터가 연결된 최소 화면'을 먼저 만든다.

### 진행 상태를 표시하는 단 4개

- **TODO:** 아직 시작 안 함
- **DOING:** 구현 중
- **BLOCKED:** 외부 결정, 오류, 환경 문제로 중단
- **VERIFIED:** 실행과 기대 결과 비교를 통과함 (작성만 완료한 것은 VERIFIED가 아님)

## 4. 3개 파일로 Product Management: PLAN / TASKS / DECISIONS

> 시험 과제 폴더의 기존 파일과 충돌하지 않도록 우선 이름과 생성 가능 여부 확인. 지침상 불필요하거나 허용되지 않는 파일이면 만들지 않는다. 자동 문서화에 시간을 쓰지 말고 **짧은 스냅샷**만 남긴다.

### `PLAN.md` — 무엇을 왜 만들고 무엇이 완료인가

```md
# PLAN
## 제품 목표
- 사용자: ...
- 해결할 업무 문제: ...
- 성공 조건: ...

## 요구사항 추적
| ID | 요구사항 | 근거 | 필수/선택 | 완료 기준 | 상태 |
|---|---|---|---|---|---|
| R01 | ... | 과제 README §... | 필수 | 실제 입력 A → 결과 B | TODO |

## 현업 협의
| ID | 쟁점 | 확인된 사실 | 제안/결정 | 상태 | 영향 |
|---|---|---|---|---|---|
| H01 | ... | ... | ... | 승인/미확정 | R01 |

## 범위 밖 / 미확정
- ...
```

- README의 **필수사항은 자동으로 범위 밖으로 빼지 않는다**.
- 기술적 세부 작업보다 **사용자가 기대하는 결과와 수용 기준**을 우선 기록한다.
- 현업과 합의해도 시험의 상위 필수조건을 무시하면 안 된다.

### `TASKS.md` — 지금 어디까지 됐고 무엇이 막혔나

```md
# TASKS
| ID | 관련 요구사항 | 작업 | 우선순위 | 상태 | 검증 근거 | 차단 사항 |
|---|---|---|---|---|---|---|
| T01 | R01 | ... | P0 | DOING | - | - |
```

- **P0:** README 필수 기능/실행·제출을 막는 오류.
- **P1:** 중요한 경험·안정성·필수 범위 내 품질.
- **P2:** 과제상 선택인 확장 기능.
- 시험 필수 요구사항은 임의로 P2로 낮추지 않는다.
- 15~25분마다 모든 행을 갱신하지 말고 **변경된 작업만 갱신**한다.

### `DECISIONS.md` — 왜 이런 방식을 선택했나

```md
# DECISIONS
## D01 — [결정 제목]
- 문제/목표: ...
- 선택: ...
- 대안 및 트레이드오프: ...
- 선택 이유: ...
- 실제 구현 위치: 파일/함수 ...
- 검증 결과: 테스트/실행 사실 ...
- 한계/미확정: ...
```

- 개발 중 중요한 설계 결정이나 실패→수정→재검증만 기록. 사소한 CSS 수정까지 쓰지 않는다.
- 파일명, 함수명, 성능 수치, 테스트 결과를 추측하지 않는다.
- **서술형 대비**는 모범답안 암기가 아니라 자기 프로젝트의 선택을 설명할 근거를 축적하는 것이다.

## 5. 현업 AI 담당자 인터뷰 플레이북

### 목표: 질문을 많이 하는 것이 아니라 *결정 가능한 조건*으로 바꾸기

1. **문제:** 어떤 사용자에게 언제 어떤 실패가 발생하나?
2. **규모:** 얼마나 자주, 몇 명에게, 어떤 상황에서 발생하나? 수치가 없다면 데이터로 검증 가능한가?
3. **하드/소프트 제약:** 반드시 지켜야 하는 규칙 vs 가급적 만족할 목표는?
4. **충돌:** 비용 vs 편의, 정확성 vs 시간, 안정성 vs 확장성 중 무엇이 우선인가?
5. **역제안:** A/B 대안을 내가 먼저 제시하고 각각 영향 설명.
6. **확정:** 무엇이 승인되었고, 보류되었고, 기본값은 누가 결정하는가?

### 현업 담당자에게 직접 쓸 질문 예시

```text
현재 가장 중요한 불편이 무엇인지, 영향을 받는 사용자와 발생 시점을 알려주실 수 있을까요?
```

```text
말씀하신 목표를 구현하려면 선택이 필요합니다.
A안: 사용자 편의 우선 — [장점], [단점]
B안: 운영 효율 우선 — [장점], [단점]
어느 목표가 우선인가요? 결정이 어렵다면 관리자가 조정할 수 있는 옵션으로 설계해도 될까요?
```

```text
확인 차 정리드리면 [확정 조건]은 필수, [기준]은 권고, [미정 항목]은 운영자가 설정하는 방향으로 이해했습니다.
이 범위로 개발을 진행해도 될까요? 아직 승인되지 않은 조건은 미확정으로 표시하겠습니다.
```

### 담당자가 모른다고 하거나 회피할 때

- 같은 질문을 반복하지 말고 **구체적인 선택지**를 제시한다.
- 그래도 결정되지 않으면 **가정임을 표시**, 필요 시 관리자 설정으로 분리하거나 제한사항으로 기록한다.
- README에 정의된 필수조건은 미확정이라는 이유로 삭제하지 않는다.
- 현업과 채팅하는 모든 내용을 Codex에 옮길 필요는 없다. **의사결정에 영향 있는 사실만 전달**한다.

## 6. 단계별 Codex CLI 프롬프트 — 순서대로 복사해 사용

### [P0] 시작: 지침 로드 및 환경 구분 (0분)

```text
이 작업 환경은 Codex CLI 개발 창과 별도의 AI 현업 담당자 채팅창으로 구성돼. 현업 채팅은 자동으로 공유되지 않으며, 내가 전달하는 내용만 현업 확인 정보로 취급해.
현재 과제의 README와 시험 규정이 이 범용 가이드보다 우선이야.
우선 실제 과제 README, 파일 구조, 제출조건, 실행 환경을 읽고 요약해. 범용 가이드 파일로 과제 README를 덮어쓰거나 시험 데이터를 외부에 업로드하지 마.
코드 수정은 아직 시작하지 마. 먼저 내가 결정해야 할 사항을 알려줘.
```

### [P1] 요구사항 감사: 구현 전 허점 발견 (0~20분)

```text
실제 과제 README와 제공 데이터를 근거로 다음을 분석해.
1) 필수/선택/비기능 요구사항, 완료 조건, 제출물
2) 데이터 파일의 구조, 식별자 관계, 누락/중복/경계값 위험
3) 서로 충돌하거나 모호한 규칙, 숨은 가정
4) 보안 취약한 기본 구현/설정(인증, 권한, 비밀번호, 비밀정보, 입력 검증)
5) 현업 담당자에게 내가 직접 전달할 결정형 질문 최대 5개
각 주장의 근거 파일/위치를 표시하고 확인된 사실/가정/미확정을 구분해.
가능하다면 PLAN.md 초기안을 만들되 실제 과제 파일을 덮어쓰지 마.
```

### [P2] 현업 역제안 준비 (수시)

```text
현업 답변이 모호해. 지금까지 내가 전달한 사실만 근거로 핵심 쟁점의 A/B 대안을 작성해.
각 대안의 사용자 편의, 운영 효율, 구현 복잡도 및 리스크를 짧게 비교해.
현업 채팅에 직접 입력할 질문 1개와 승인 요청 문장 1개만 작성해.
현업이 승인하지 않은 사항은 확정하지 마.
```

### [P3] 계획/설계: 최소 복잡성으로 구현 (20~40분)

```text
PLAN.md와 확인된 운영규칙을 기준으로 P0 기능부터 구현할 3~5개 작업 묶음을 설계해.
프론트엔드, HTTP/API, 핵심 비즈니스 로직/알고리즘, DB/저장소의 책임 경계를 설명해.
입력 → 검증 → 계산 → 저장 → 조회 → 화면 렌더링의 흐름을 파일/모듈 수준으로 제안해.
동기/비동기, 트랜잭션, 별도 작업 큐는 필요성과 이유가 있을 때만 도입해. 과도한 설계는 피하고 각 선택의 대안/트레이드오프를 간략히 설명해.
각 작업의 완료 조건과 실행 테스트를 TASKS.md에 적어. 내가 판단해야 할 큰 결정만 요청해.
```

### [P4] 핵심 구현: 실제 데이터 우선 (40~115분)

```text
승인된 다음 P0 작업 묶음을 구현해. 먼저 실제 데이터로 동작하는 최소 입력→출력 흐름을 완성해.
화면만 보이는 더미 데이터와 실제 연동 결과를 혼동하지 마. 기존 기능이 깨지지 않도록 작은 단위로 수정해.
수정 후 실제 명령을 실행하고 정상/오류/경계값 사례를 테스트해.
작업 완료 시 [구현 파일][실행/테스트 실제 결과][남은 문제][다음 작업]만 짧게 보고하고 TASKS.md/DECISIONS.md의 변경된 부분만 갱신해.
중요한 제품 범위나 운영규칙을 변경해야 한다면 먼저 내 결정을 요청해.
```

### [P5] 작업 게이트: 매 15~25분 또는 묶음 완료 시

```text
현재 작업을 잠시 정리해. 아래 다섯 항목으로 10줄 이내 보고해.
1. 완료: 수정한 파일과 실제로 동작하는 기능
2. 증거: 실행한 명령, 통과/실패 테스트
3. 위험: 가장 큰 미검증 사항 1~3개
4. 판단: 변경한 설계와 그 이유
5. 다음: 남은 시간에서 가장 중요한 1개 작업
구현만 하고 검증하지 않은 작업은 VERIFIED로 표기하지 마.
```

### [P6] 검증: 보안/정합성/예외 테스트 (115~165분)

```text
새 기능 추가를 잠시 멈추고 실제 과제 README와 PLAN.md를 기준으로 검증해.
필수 요구사항별 정상·빈값·오류·경계 조건, 데이터 정합성, 인증/권한, 비밀번호 해싱, 비밀정보 노출, 입력값 검증을 확인해.
동시 수정이 있는 경우 중복 처리/트랜잭션 위험을 점검해. 오래 걸리는 작업이 있는 경우 응답성 및 실패 복구 방식도 확인해.
각 테스트의 실행 명령, 예상 결과, 실제 결과를 PASS/FAIL/NOT TESTED로 구분해.
실패는 원인을 수정한 뒤 같은 테스트를 재실행하고, 테스트를 지워서 통과시키지 마.
README가 요구하는 Docker/PORT/실행조건을 확인하되, 명시되지 않은 배포 작업을 임의로 확대하지 마.
```

### [P7] 오류 대응: 401, 실행 실패, 데이터 불일치 등

```text
현재 오류를 현상 → 재현 방법 → 실패 구간 가설 → 근거 로그 → 수정 → 동일 테스트 재실행 순으로 분석해.
프론트 표시, API 요청/응답, 인증, 비즈니스 로직, DB 계층 중 어느 부분에서 발생했는지 먼저 좁혀줘.
보안 검증을 우회하거나 데이터를 하드코딩해 오류를 숨기지 마.
고칠 수 없는 환경 문제라면 실행한 명령, 오류 메시지, 남은 위험을 사실대로 기록하고 우회 금지 규정을 준수해.
```

### [P8] 설명 준비: 서술형 전 내 이해 확인 (과제 풀이 단계에서만)

```text
내가 AI 없이 시스템을 설명할 수 있도록 실제 코드에 근거해서 1페이지 분량으로 요약해.
① 해결한 문제와 필수조건 ② 입력→알고리즘→저장→API→화면 흐름 ③ 주요 파일/함수 역할
④ 설계 선택 이유와 트레이드오프 ⑤ 보안/동시성/에러 처리 ⑥ 실제 실패·수정·검증 결과
각 항목은 비전공자도 이해할 말로 2~3문장 이내로, 실제 파일명과 검증 사실을 덧붙여 줘.
구현하지 않은 기술이나 테스트를 구현했다고 쓰지 마. docs/essay-prep.md를 생성할 수 있는 경우 과제 풀이 단계에서만 저장해.
후속 서술형 시작 후에는 AI 지원을 중단해.
```

### [P9] 마감: 신규 기능 중지 및 제출 (165~180분)

```text
이제 신규 기능 개발을 중단해. 실제 과제 README에 나온 제출 요건과 현재 파일 상태를 대조해.
필수 파일, 경로, 저장 여부, 서버 실행, Docker/PORT 조건(명시된 경우), 테스트 실패 항목, 민감정보 노출 여부를 확인해.
최종 보고는 [필수 요구사항 충족 상태][실행 증거][미해결 사항][제출 전 반드시 할 일]로 짧게 작성해.
플랫폼 제출/확정 조작은 내가 직접 한다. 서술형 단계에는 AI를 사용하지 않는다.
```

## 7. 품질 검증: 코딩 전문가가 아니어도 확인할 수 있는 질문

### A. 실제 기능

- 실제 입력을 바꾸면 **실제 계산 결과가 달라지는가**? 고정된 더미 화면은 아닌가?
- 원본 데이터의 특정 행을 샘플링해 출력과 비교했는가?
- 필수조건을 위반하면 잘못된 결과를 저장하는 대신 실패 상태를 알리는가?
- 저장된 결과를 다시 조회했을 때 동일한가? (Create → Read; 필요 시 Update/Delete도 확인)

### B. 데이터·알고리즘

- 입력값, 단위, ID/키 관계, 누락값을 검증했는가?
- Hard Constraint(반드시 준수)와 Soft Constraint(개선 목표)를 구분했는가?
- 비용 함수/최적화 방식을 왜 선택했는가? 빠르지만 최적해를 보장하지 않는다면 그렇게 설명할 수 있는가?
- 생성기와 검증기의 책임이 섞여 있지는 않은가? **분리 필요성이 없는 작은 시스템에 과한 구조를 강요하지 않는다.**

### C. 기본 보안

- 비밀번호를 평문이나 단순 MD5/SHA-256 단독 해시로 저장하지 않는가? 전용 비밀번호 해싱(예: Argon2id, bcrypt)과 적절한 설정을 검토했는가?
- 인증(401)과 권한(403) 문제를 구분하고 정상/비정상 접근을 테스트했는가?
- API 키, 토큰, 비밀번호가 코드/로그/화면에 노출되지 않는가?
- 입력 검증/쿼리 파라미터화를 적용했는가? 보안 검증을 임의로 비활성화하지 않았는가?

### D. 실행·성능·인수인계

- 과제에서 요구하는 포트와 Docker 실행 방식이 실제로 되는가?
- 계산이 오래 걸려 타임아웃이 난다면 동기/비동기 분리가 필요한가? 무조건 메시지 큐부터 도입하지 않는다.
- 응답 속도/부하를 시험했다면 **실제 측정값**만 보고하는가?
- 설치·실행 방법을 다음 사용자가 따라 할 수 있는가?

## 8. 예상치 못한 상황별 운영 원칙

| 상황 | 즉시 대응 | 하지 말 것 |
|---|---|---|
| 현업이 모른다고 답함 | A/B 옵션 제시 → 승인 요청 → 미확정 기록 | 승인받았다고 꾸며 쓰기 |
| 요구사항과 현업 발언 충돌 | 상위 과제 README 기준 확인, 명시적 재질문 | 필수조건 임의 삭제 |
| UI만 빠르게 완성됨 | 실제 데이터→API→화면 관통 테스트 우선 | 장식 추가에 시간 사용 |
| 코드가 복잡해짐 | 목적에 불필요한 계층·큐·라이브러리인지 검토 | 어려운 설계를 성과로 포장 |
| 로그인 401 오류 | 인증 흐름 단계별 추적, 정상/비정상 재테스트 | 인증 우회 |
| 데이터 누락/이상값 | 오류 위치와 정책 명시, 입력 검증 | 조용히 버리거나 가짜 값 생성 |
| 빌드/네트워크 차단 | 환경 제약 기록, 허용 범위 내 대안 검토 | 권한·보안 우회 |
| 시간 20분 남음 | 신규 기능 동결, 제출 요건부터 확인 | 대규모 리팩터링 시작 |
| 서술형 시작 | AI 사용 중지, 본인 기억과 이해로 직접 작성 | AI 답변 조회/복사 |

## 9. 후속 서술형 6문항: 개발 중 익혀야 할 이해 항목

> 아래는 **실제 문항이 아니라 연습용 관점**이다. 실제 후속 문항은 제출 시스템과 다를 수 있다. 개발 단계에서만 Codex로 설명을 듣고, 이후 AI 없는 5분/문항 형식에 대비한다.

| 관점 | 스스로 설명할 질문 |
|---|---|
| 문제/현업 협의 | 어떤 요구가 모호했고 어떤 제안을 통해 어떻게 결정했나? |
| 데이터 처리 | 파일 입력에서 검증·변환·저장·JSON/화면까지 무엇이 이어지나? |
| 아키텍처 | HTTP/API, 서비스/알고리즘, DB 경계는 어디이며 왜 나눴나? |
| 알고리즘 | 무엇을 최적화하고 무엇을 반드시 지켜야 하나? 대안과 트레이드오프는? |
| 동기/비동기·트랜잭션 | 오래 걸리는 작업이나 동시 변경을 어떻게 처리했나? |
| 보안/디버깅/검증 | 발생한 오류를 어떻게 추적했고 어떤 테스트로 수정 확인했나? |

**답변 기본 구조:** `문제/목표 → 실제 구현(파일·함수) → 이유/대안 → 테스트/한계`.  
**지키기:** 실제 구현하지 않은 메시지 큐, 프레임워크, 검증 방식을 사용했다고 말하지 않는다.

## 11. 참고: 이 매뉴얼의 위치와 한계

- 특정 회사의 실제 업무 정책, 통근버스 운영기준, 최적화 알고리즘을 미리 강제하지 않는다. 과제마다 먼저 확인한다.
- 출제자의 공식 채점 배점/세부 알고리즘은 공개되지 않았으므로 여기서 추정한 워크플로우가 고득점을 보장하지 않는다.

- 이 저장소에는 실제 시험 문제·데이터·답안·스크린샷·작업 로그를 포함하지 않는다.
